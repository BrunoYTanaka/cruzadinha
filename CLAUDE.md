# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Where things stand

This repository ("cruzadinha") is driven by a [GitHub Spec Kit](https://github.com/github/spec-kit) scaffold (v1.0.13, Claude integration, `sh` scripts, sequential feature numbering). Features 001 to 048 are built; each has its reasoning, findings and tests in `specs/NNN-*/` and its history in git and `CHANGELOG.md`. Only the rules a new change can break are kept here.

**Product**
- Crossword site with four puzzle sources (`oglobo`, `cruzadaonline`, `cruzadasbrasil`, `clube`; names in `puzzleSourceNames` in `shared`, the lists derive from `puzzleSourceIdSchema.options`, default source is the first). Anyone with the URL plays as a guest; accounts add progress saved on the server. Feature 001 verdict (viable) and the O Globo API details are in `specs/001-viabilidade-fonte/decision.md`.
- Guest progress, clock, helps, completion and record live only in IndexedDB (`idb`, database `cruzadinha-visitante`, `features/guest/`); guest and account data never mix. A `game` generation on the record makes a tab opened before "Jogar de novo" unable to overwrite the reset (feature 036).
- User settings are one record (`settingsSchema` in `shared`): on the device in `cruzadinha:settings`, for accounts in `user_settings` with `GET`/`PUT /api/settings` (newest `savedAt` wins; after login the account wins).

**API (`apps/api`)**
- Auth: invite-only registration is gone. Sign-up (behind `REGISTRATION_ENABLED`, default `false`; closed answers `403 registration-closed` first) stores a `pending_registrations` row and e-mails a link; the password is chosen at `verify-email` (validated before the token is consumed). `forgot-password`/`reset-password` work with sign-up closed and end every session of the user. Every e-mail route answers `202 { retryAfter }` the same with or without an account; `429` is only the per-address limit. E-mail sits behind `EmailSender` (`modules/email/`); without `RESEND_API_KEY` production answers `503 email-unavailable`. Tests that need an account use `signUpForTest` (`apps/api/src/test/app.ts`) or the CLI. Sessions are server-side (sliding 30-day expiry, 1-year limit), tokens stored only as SHA-256. Data: `docs/data-definitions/DDE-005-*`, ERD-005.
- Rate limits live in `rate_limit_attempts`. Use `rateLimiter.reserve` (or `admitAddress`) so simultaneous requests cannot pass the limit; never `check` then record (`record` is gone). The e-mail daily ceiling reserves before sending and releases when nothing left. `reserve` does not prune: `auth cleanup` deletes every attempt older than 2 days.
- Puzzles: one row per source, level and date; public part and solution in separate `jsonb` columns. `GET /api/puzzles` and `/api/puzzles/:id` return `{ puzzleId, puzzle, solution }` after the service revalidates the pair (a mismatch answers a generic 500); a missing past date is fetched from the source behind the persisted per-address `PUZZLE_FETCH` limit, and only within 366 days back (`FETCH_WINDOW_DAYS`; older unsaved days answer 404 without a request; saved ones are still served). Routes with an optional session (`createOptionalSession`) serve guests; an invalid cookie answers `401` and clears it. Sources with `onDemand: false` (`clube`) are collected newest-first via `listRecent` and never fetched from `getByDate`. Library (`GET /api/library`, optional `source`) never selects `data`, `solution` or `cells` and never reaches the source.
- Progress: composite key `(user_id, puzzle_id)`, the user always comes from the session; the server checks only the letter format, the front end decides completion. Rules are the pure `decideSave`/`decideReset`. `PUT`/`POST /api/progress` count per user (`PROGRESS_SAVE`, key type `USER`, 1800 per hour) and answer `429`; the site's save queue retries a 429 with its backoff.
- Sources: one folder per adapter under `sources/`, no adapter imports another; shared XML reader and clue cleanup in `sources/common/`. Real-source findings: `specs/003-*`, `014-*`, `029-*`, `030-*` (`findings.md`). `clube` runs an obfuscated script in QuickJS/WebAssembly with no host functions.
- Collect: `puzzles collect` reports per source, a failure in one never stops the others, and an unexpected adapter error reaches `PuzzlesDeps.onError` (the CLI writes `[Source] Erro em <date>: <names and codes>`; a listed source reports the edition being loaded). `collect.yml` opens one `fonte-quebrada` issue per source with a `[Source] Falhou em` line (no duplicate while one is open; rate-limit stops and non-source failures open none).
- Deploy: `PROXY_SECRET` is required in production (`loadConfig(env, { requireProxySecret: true })`, only for `server.ts`); the Pages Function in `apps/web/functions` adds the secret and client IP, and `src/http/proxy-guard.ts` refuses (`403`) anything else except `/api/health`, and limits count an IPv6 client by its /64 block (`limitKey`; IPv4-mapped counts as the IPv4). The Function gives the API call a 25 s timeout. Response schemas in `shared` are tolerant (unknown keys dropped), request schemas and the puzzle/solution format are strict, so an older site accepts a newer API.

**Site (`apps/web`)**
- After the game loads nothing may stop the player: network failure, save errors and an expired session are non-blocking notices. A session that ends off the board turns the person into a guest. The site waits for the free API to wake (`api/server-wake.ts`, `whenServerReady`; `useSessionQuery` is enabled only when the server is ready) and reloads once when an old tab fails to load a lazy chunk after a deploy.
- No route requires a session (`viewerLoader`, `useViewer`). The landing is `/` and the calendar is `/calendario` (feature 048). Calendar: opens on the default source, or on the game's source when coming back from a game (`source-choice.ts`, a module variable); a "Hoje" section has one card per source; fetchable days go to `/dia/:date?fonte=<source>`; a source the API refuses (400 from an older API) shows "Esta fonte não está disponível agora".
- Game screen: desktop layout only above 860 px and without the on-screen keyboard (`useDesktopLayout`); the board grows to the largest cell that fits, resizable with `components/ResizeHandle` (30 to 110 px per cell; calendar width 720 to 1600 px). The clue bar takes the board width, stays on one line (ellipsis, full clue in a balloon after 500 ms of mouse rest, above the bar), and nothing may shift the layout while typing (`e2e/sem-saltos.spec.ts` measures it). A solved clue (word complete and equal to the solution, compared with `plainLetter`) is struck with a check mark; `strikeMode: 'filled'` shows only the strike. With `copyClue` on, a double click copies `clue (length): letters`, never the solution. Help limits come in the reducer action. The solution can carry accented letters, so always compare with `plainLetter`.
- UI rules: `components/Button` has four variants (`primary`, `secondary`, `quiet`, `icon`) plus `size: 'small'` and `block`; buttons never use the link colour (except primary) and are never underlined, text links stay underlined; `global.css` declares `@layer reset, components` and selected styles use `background-color` so the hover/pressed overlay survives. One `h1` per page (`ErrorState` takes `level: 1 | 2`). `Tooltip` keeps itself inside the window. The theme button is a View Transition circle (instant with reduced motion). `Dialog` with `closeOnBackdrop` closes only when the press also started outside the panel; an open settings dialog suspends the clock.
- Build: `vite.config.ts` imports `./version-plugin.ts` with its extension so it loads with `--configLoader native`; never silence the warning with `VITE_CONFIG_NATIVE_IGNORE_WARNING`. `react` and `vendor` are split with `codeSplitting.groups`. `public/_headers` sets `noindex, nofollow` on `/*` with `! X-Robots-Tag` on `/`, `/sitemap.xml` and `/robots.txt` (only the landing is indexable, constitution 5.0.0), caching, and `Referrer-Policy: no-referrer` on the e-mail link routes; the token travels in the URL fragment and is read once.

## Commands

Prerequisites: Node.js 24 (`nvm use`, version in `.nvmrc`) and, for the local environment, Docker with Compose.

Run everything from the repository root:

- `npm ci`: install all workspaces from `package-lock.json`; also activates the Git hooks (`prepare: husky`).
- `npm run format` / `npm run format:check`: Prettier on the whole repo (`specs/`, `.specify/`, `.claude/` and this file are ignored).
- `npm run lint`: ESLint with the single root `eslint.config.mjs`.
- `npm run check:branch [name]`: fails when the branch name (default: current) is not `<type>/<kebab-description>` (`scripts/check-branch-name.mjs`).
- `npm run check:ids` / `npm run check:ids:remote`: fail when two `specs/NNN-*` folders, two `DDE-NNN` or two `ERD-NNN` files share a number (`scripts/check-unique-ids.mjs`). Spec Kit and the doc skills pick the next number from the local tree only, so parallel branches can collide; `:remote` also fetches `origin/main` and compares against it (offline it warns and checks only the local tree). If it fails, rename the folder to the next free number, update `.specify/feature.json` if it points to it and the references inside the feature's files, and keep the branch name when a pull request is already open (renaming the head branch closes the PR).
- `npm run check:deps`: dependency-cruiser (`.dependency-cruiser.cjs`) checks the boundary rules of feature 037 (listed under Architecture) and file-level import cycles in `apps/web/src` and `apps/api/src`; every rule is an error, and `npm run lint` runs it after ESLint (so the CI lint step, the pre-push hook and `npm run lint` fail on a violation). Test files, `src/test/` and `e2e/` are not checked.
- `npm run typecheck`, `npm test`, `npm run build`: run in every workspace (`--workspaces --if-present`).
- `npm run test:int`: integration tests (`*.int.test.ts`) against a real Postgres 17 started by Testcontainers; needs Docker. Not run by the pre-push hook.
- Single test: `npx vitest run <file>` inside the workspace, e.g. `cd apps/api && npx vitest run src/config.test.ts`.
- `npm run source:check -w @cruzadinha/api -- [YYYY-MM-DD] [--save]`: fetches the puzzle from the real source (real requests, never run by the test suite or CI); `--save` writes the raw bodies to the git-ignored `apps/api/.source-samples/`.
- `npm run source:check:cruzadaonline -w @cruzadinha/api -- [YYYY-MM-DD ...] [--save]`: same check for the Cruzada Online source, up to 10 dates with a 2 s pause and one line per date (future dates are refused without a request); `--save` writes `cruzadaonline-<date>.xml` to `apps/api/.source-samples/`.
- `npm run source:check:cruzadasbrasil -w @cruzadinha/api -- [YYYY-MM-DD ...] [--save]`: same check for the Cruzadas Brasil source (up to 10 dates, 2 s pause, one line per date, future dates refused without a request); `--save` writes `cruzadasbrasil-<date>.html` to `apps/api/.source-samples/`.
- `npm run source:check:clube -w @cruzadinha/api -- [YYYY-MM-DD ... | --count=N] [--save]`: same check for the Cruzadas Clube source (real requests with a 2 s pause, one line per edition; with no date the newest edition, `--count` up to 10 newest, dates select editions by the date on their page; `--save` writes the page, script and extracted XML to `apps/api/.source-samples/`).
- `npm run db:generate -w @cruzadinha/api` (add `-- --name <name>`, or `-- --custom --name <name>` for hand-written SQL such as triggers): generate a migration from `src/platform/db/schema.ts` into `apps/api/drizzle/`. Never use `drizzle-kit push`.
- `npm run db:migrate -w @cruzadinha/api`: apply pending migrations to `DATABASE_URL` (idempotent). The API also applies them on startup; in the image it is `node apps/api/dist/migrate.mjs`.
- `npm run db:seed -w @cruzadinha/api`: development only; creates the test account from `SEED_USER_EMAIL`/`SEED_USER_PASSWORD` (fictitious values in `.env.example`) never changes an existing account, also saves a sample 5 x 5 puzzle (invented text, attributed as a sample) for today in Brasília without touching the network or an existing puzzle (while it occupies today, `puzzles collect` counts today as already saved: recreate the local database to collect the real one), refuses `NODE_ENV=production` and is not in the image.
- `npm run cli -w @cruzadinha/api -- users create --email <email>`: author CLI that creates an account even with sign-up closed (password asked twice without echo, or the first line of stdin; never an argument); exit 1 if the e-mail exists, 2 for invalid input. In the image it is `node apps/api/dist/cli.mjs`.
- `REGISTRATION_ENABLED` (`true`/`false`, default `false`): opens sign-up on the site and the API; set it only in the Render dashboard (`sync: false` in `render.yaml`) and restart.
- `npm run cli -w @cruzadinha/api -- auth cleanup`: deletes pending registrations and password-reset tokens expired or used more than 7 days ago and every rate-limit attempt count older than 2 days (`reserve` does not prune) (feature 035); run twice a day by `collect.yml`. In the image it is `node apps/api/dist/cli.mjs auth cleanup`.
- E-mail for sign-up and recovery (feature 035): `RESEND_API_KEY`, `MAIL_FROM`, `APP_BASE_URL` (all three or none; set only in the Render dashboard) and the `EMAIL_*` limits. Without the key, development writes the link to the API log and production answers `503 email-unavailable`. Names, ranges and defaults: `docs/deploy.md`.
- `npm run cli -w @cruzadinha/api -- puzzles collect`: for each source in order (one summary line per source, failures prefixed with the source name), saves today's puzzle (Brasília) and the missing past days within `COLLECT_HISTORY_DAYS` (0 to 365, default 31; real requests with a 2 s pause, one per missing date, stops on the source's rate-limit signal). Idempotent: dates already saved are not requested. After the sources it deletes dead sessions (expired, or ended more than 7 days ago) and prints `Sessões apagadas: N.`; a failure there prints `Falha ao apagar sessões antigas.`, never hides what was saved and exits 1. Exit 0 on success, 1 on failure or interruption. The scheduled workflow `collect.yml` runs it from the built files and needs the `DATABASE_URL` secret (without it the schedule is skipped with a notice; it does not run migrations, the API does that on startup). `COLLECT_HISTORY_DAYS` can also be set as a repository variable.
- `npm run dev -w @cruzadinha/api`: API with reload (`tsx watch`), reading `.env` from the root. The Swagger UI is at `http://localhost:3000/api/docs/` (also through the Vite proxy) and the OpenAPI 3.1 document at `/api/docs/json` and `/api/docs/yaml`. Docs are never registered in production, including the `docker compose` API (production image), where `/api/docs*` returns 404.
- `npm run test:e2e -w @cruzadinha/web`: Playwright (Chromium) against `vite preview`; needs the API and a local Postgres running with the seed, and `DATABASE_URL` set (the support code truncates tables and refuses a non-local database or `NODE_ENV=production`). Run `npx playwright install chromium` once. CI runs it in the `e2e` job. Locally, to keep the development data, point it at a separate database (e.g. `cruzadinha_e2e`) with its own API: `DATABASE_URL=<e2e db> PORT=3001` for the API and `DATABASE_URL=<e2e db> API_PROXY_TARGET=http://localhost:3001 E2E_WEB_PORT=4174` for the run (see `specs/011-calendario-e-tamanho-tabuleiro/quickstart.md`).
- `npm run dev -w @cruzadinha/web`: site with Vite; `/api` is proxied to `API_PROXY_TARGET` (default `http://localhost:3000`).
- Deploy (feature 012): automatic after a release (see `docs/versionamento.md`); manual redeploy or rollback with `gh workflow run deploy.yml -f api=<version|ultima|atual> -f web=<version|ultima|atual>`. Manual Pages commands use `npx wrangler@4.151.1` (no wrangler dependency in the repo). Runbook in `docs/deploy.md`.
- Front variables: `VITE_HELP_LETTER_LIMIT` (default 4) and `VITE_HELP_WORD_LIMIT` (default 2) are read at build time from the root `.env`; invalid values abort start-up.
- Local environment: `cp .env.example .env`, then `docker compose up -d` (Postgres 17 and the API image). Health: `curl localhost:3000/api/health`.
- `PROXY_SECRET` is required when `NODE_ENV=production`: the server (not the author CLI) refuses to start without it. `docker-compose.yml` sets `ALLOW_MISSING_PROXY_SECRET: 'true'` so the local production image runs without the site proxy; never set it on Render.

Hooks: pre-commit runs `lint-staged` (ESLint `--fix` and Prettier on staged files); pre-push runs `check:branch`, `check:ids:remote`, `check:deps`, `typecheck` and the unit tests. CI (`.github/workflows/ci.yml`) runs a `branch-name` job on pull requests (head branch must be `<type>/<kebab-description>`; `main` and `release-please--*` are exempt; make it a required check) and runs `npm ci`, `check:ids`, `format:check`, `lint`, `typecheck`, `test` and `build` on every push, plus a job that runs `test:int` and one that builds `apps/api/Dockerfile`.

## Architecture

npm workspaces monorepo, TypeScript 6 strict everywhere (`tsconfig.base.json`, extended per package):

- `packages/shared` (`@cruzadinha/shared`): Zod schemas and types shared by API and web. No build step: it exports its TypeScript source (`./src/index.ts`). `src/puzzle/` holds the internal puzzle format: the public part (`puzzleSchema`, with the consistency rules applied in `safeParse`) and the solution (`solutionSchema`) are separate, so the public part has no field for answer letters (the API response carries both, see feature 007).
- `apps/api` (`@cruzadinha/api`): Fastify 5. `src/app.ts` builds the app without listening (tested with `app.inject()`); `src/server.ts` is the entry point. Layers per module: route → service → repository (`src/modules/<name>/`, database access in `src/platform/db/`). Configuration comes only from environment variables validated by `src/config.ts`; no other module reads `process.env`. Built with tsdown into `dist/server.mjs`, `dist/migrate.mjs` and `dist/cli.mjs` (plus a shared chunk), inlining `shared`; the Dockerfile also copies `apps/api/drizzle/`.
  - `src/platform/db/`: postgres.js + Drizzle client (`client.ts`), schema (`schema.ts`), the shared `timestamps` columns (`columns.ts`; every table must spread them and get a `<table>_set_updated_at` trigger in its migration, enforced by `conventions.int.test.ts`), `migrations.ts` and error helpers. Drizzle's `DrizzleQueryError` message embeds query parameters (hashes, e-mails), so logs use `describeError` (names and codes only).
  - `src/modules/identity` (`sessions/` login, logout, `me`, session `preHandler` with sliding renewal, optional-session `preHandler` for the routes open to guests; `registration/` register behind `REGISTRATION_ENABLED`, `GET /api/auth/registration`, verify e-mail, `createAccount` for the CLI, resend; `recovery/` forgot and reset password; `index.ts` is what other modules import) and `src/platform/rate-limit` (attempts stored in the database; `index.ts` is its only entry, like `src/platform/email`). Passwords use argon2id; session tokens are stored only as SHA-256. Services take an injectable `Clock`.
  - `src/platform/docs/`: OpenAPI docs (`@fastify/swagger` + `@fastify/swagger-ui`), registered only outside production. Each route declares a `schema` (tags, summary, body, responses, `security` when it needs a session) in `<module>.schemas.ts`, built from the `shared` Zod schemas with `toDocSchema`. These schemas only document: `buildApp` swaps in pass-through validator and serializer compilers, so validation stays in each route's `safeParse`. Every new `/api/*` route needs a `schema`, enforced by `src/platform/docs/docs.test.ts`.
  - `src/modules/puzzles` (`GET /api/puzzles`, `GET /api/puzzles/:id`, `collect()`): the service reads the saved puzzle first and only calls the `PuzzleSource` for a missing, non-future date, after checking the `PUZZLE_FETCH` limit; it revalidates the puzzle/solution pair before saving with `onConflictDoNothing`. Date helpers (Brasília day, candidate dates) are in `src/platform/lib/dates.ts`.
  - `src/modules/library` (`GET /api/library`): read-only listing of saved puzzles with the user's progress summary; see feature 009 above.
  - `src/modules/settings` (`GET`/`PUT /api/settings`): the account copy of the user settings in `user_settings`; see feature 021 above.
  - `src/platform/http/proxy-guard.ts`: proxy secret check and `request.clientAddress` (feature 012); `src/version.ts`: `API_VERSION` from `package.json`.
  - `src/cli.ts` / `src/cli/run-cli.ts`: author CLI that calls the auth (`users create`) and puzzles services directly. `src/sources/` holds the `PuzzleSource` interface (`types.ts`) and one folder per adapter; `oglobo/` is the only code that knows the Agilmente API (request, anonymous token, response schema, pure ipuz → internal conversion) `cruzadaonline/` the only code that knows the Público XML (request, safe XML reading, schema, pure Crossword Compiler → internal conversion, clue text cleanup) and `cruzadasbrasil/` the only code that knows the Cruzadas Brasil page (request, game-data extraction from the Next.js payload, schema, pure conversion, clue text cleanup). The safe XML reader (`xml.ts`) and the clue text cleanup (`clue-text.ts`) used by `cruzadaonline/` and `clube/` live in `sources/common/`; no adapter imports from another. `buildApp` and the CLI pass the four adapters to the puzzles service. Their tests use an injected `fetch` and reduced 5 x 5 fixtures with invented content, never full puzzles from the source.
- `apps/web` (`@cruzadinha/web`): React 19 + Vite 8; server state through TanStack Query. The pure board logic (reducer, navigation, helps, completion) is in `src/domain/game/` (not a separate package) and the visitor's pure rules in `src/domain/guest/`. `src/pages/` has one folder per route; `src/features/` holds `session`, `account`, `guest` (visitor progress in IndexedDB through `idb`), `library`, `settings`, `game` and `status`; `src/shared/services/api/` is the single HTTP client (Zod-validated, `ApiRequestError`); `src/shared/themes/` has the tokens (light/dark) and the theme button; `src/shared/components/` the generic pieces (Button with the four types and `buttonClass`, Pill, Dialog, Notice, ResizeHandle). Tests use `src/test/` helpers (`render`, `http`, `fixtures`, `game-harness`, which also opens the game as a guest) and `vitest-axe`, with `fake-indexeddb` reset before each test; end-to-end specs are in `apps/web/e2e/`.
  - `functions/` holds the Cloudflare Pages Function (`api/[[path]].ts` → `proxy.ts`, tested in node); `version-plugin.ts` writes `dist/version.json`; `public/_headers` sets `noindex` and cache rules; `robots.txt` and `sitemap.xml` are generated by `prerender-plugin.ts`.
- The API and the web app never import each other; anything both need goes in `shared`.

Unit tests use Vitest 5 per workspace (`jsdom` + Testing Library in web) and never touch the network, a database or a browser. Integration tests live in `apps/api/src/test/*.int.test.ts`, run by `vitest.int.config.ts` (`npm run test:int`): the global setup starts `postgres:17-alpine` with Testcontainers and applies the migrations, files run serially and tables are truncated before each test.

Tooling notes: ESLint 10 with a `package.json` `overrides` entry so `eslint-plugin-jsx-a11y` (peer range stops at ESLint 9) accepts it; TypeScript stays on 6.0 because `typescript-eslint` does not support 7 yet. Writing `any` is a lint error (`@typescript-eslint/no-explicit-any`, constitution principle I); external data enters as `unknown` and goes through Zod.

## Spec-driven workflow

Work is meant to flow through the Spec Kit skills in `.claude/skills/`, in roughly this order:

1. `/speckit-constitution`: project principles live in `.specify/memory/constitution.md` (v4.0.0). Plans must pass a Constitution Check against it.
2. `/speckit-specify`: create a feature spec (`spec.md`).
3. `/speckit-clarify`: resolve underspecified areas in the spec.
4. `/speckit-plan`: generate `plan.md` and design artifacts.
5. `/speckit-tasks`: generate a dependency-ordered `tasks.md`.
6. `/speckit-analyze` and `/speckit-checklist`: check consistency and quality across the artifacts.
7. `/speckit-implement`: execute `tasks.md`. `/speckit-converge` appends any unbuilt work to `tasks.md` as new tasks.

`/speckit-taskstoissues` converts tasks to GitHub issues.

## Conventions

- Formatting (Prettier): `semi: false`, `singleQuote: true`, `trailingComma: 'all'`, `printWidth: 100`, `tabWidth: 2`.
- Commits follow [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/): `<type>[scope][!]: <description>`, types `feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`, `build`, `ci`, `chore`. Breaking changes use `!` or a `BREAKING CHANGE:` footer. Scope is the workspace or module (`api`, `web`, `shared`, `auth`, `game-logic`). Description in the imperative, lowercase, no trailing period. Commit messages (subject and body) are always written in English, e.g. `feat(game-logic): add word validation`, not `feat(game-logic): adiciona validação de palavras`.
- Versions: the API and the site have their own semver, computed by release-please from these commits. The commit type decides the bump (`fix`/`perf` → patch, `feat` → minor, `!`/`BREAKING CHANGE` → major, minor while below 1.0.0; `docs`, `chore`, `ci`, `test`, `style`, `refactor` → none) and the folder touched decides which part (`apps/api/`, `apps/web/`; `packages/shared/` bumps both as a patch). Releasing = merging the release PR; versions, tags and `CHANGELOG.md` are never edited by hand. Changes must stay compatible with the previous version of the other part (two releases to remove anything). See [docs/versionamento.md](docs/versionamento.md).
- Commit messages and PR descriptions must NOT include a `Co-Authored-By` trailer or any other Claude/AI attribution line (this overrides the default attribution).
- Branches are `<type>/<kebab-description>` with the same types; Spec Kit feature branches include the number and slug, e.g. `feat/001-viabilidade-fonte`.
- Work type decides the flow: new behavior → full Spec Kit cycle on `feat/NNN-slug`; bug fix → `fix/<slug>` without the full cycle, starting with a failing regression test (committed with the fix); a fix that changes a documented rule → update that feature's `spec.md` first and treat it as a feature; chores/docs/ci → direct, no spec.
- Issue templates (feature 026) live in `.github/ISSUE_TEMPLATE/` (`bug.yml`, `feature.yml`, `docs.yml`, `chore.yml`, plus `config.yml`, blank issues allowed) and suggest the title prefixes `[Bug]: `, `[Feature]: `, `[Docs]: `, `[Chore]: ` (the issue number is the identifier; commits and PRs keep Conventional Commits). The issue type matches the flow: bug → `fix/<slug>` starting with a failing regression test; feature → full Spec Kit cycle on `feat/NNN-slug`; docs and chore → direct, no spec. The templates only take effect on `main`.
- The design source is `docs/design.md` (the app is named Cruzadinha).

## Layout of `.specify/`

- `scripts/bash/`: helpers the skills call (`create-new-feature.sh`, `setup-plan.sh`, `setup-tasks.sh`, `check-prerequisites.sh`, `resolve-template.sh`, shared code in `common.sh`). Prefer running these over recreating their logic by hand.
- `templates/`: templates for spec, plan, tasks, and so on.
- `workflows/speckit/workflow.yml`: workflow definition.
- `integrations/*.manifest.json`: record the files Spec Kit installed. Use the Spec Kit tooling, not manual edits, to upgrade them.
- `init-options.json` and `integration.json`: install-time settings.
